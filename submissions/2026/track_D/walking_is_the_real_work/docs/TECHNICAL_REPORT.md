# 技术报告 · 散步才是正经事

赛道 D / Social Good · Gemma 4 4B Multimodal · 2026 上海赛区

## 1. 它要解决什么(产品视角)

> *让一个人,像城市感性人类学者一样,把散步当成正经事去做。*

这不是一个色彩工具,也不是一本数字日记。它是一只 *容器* —— 把街头那些
易碎的、说不出名字的、来不及拍照修图的瞬间,接住,然后归档。

**真实的痛点不是"没有 app",是"已经有太多 app"**:
小红书让你打卡,大众点评让你排队,导航让你最优路线,相册让你成片堆积。
没有任何一款产品愿意让用户 *慢下来,只看一片墙的颜色*。

我们要让用户做的事,只有三件:**走路、采一片颜色、翻看图鉴册**。

### 1.1 设计上的三选二

设计阶段我们盘出三个互斥方向,只走两条:

| 方向 | 核心 | 现在的位置 |
|------|------|-----------|
| 一·城市标本夹 | 极简地方志笔记本,大字报排版,衬线字体 | **采纳为容器** |
| 二·盲目浪漫 | 反导航,把游荡留成迷雾里的星图 | 暂留接口(底栏 *地图*),不在本次 demo 范围 |
| 三·城市色谱 | 潘通色卡式的局部色彩抽取与感性命名 | **采纳为肌肉** |

最终交付是 **一 + 三的融合**。这一节的目的不是炫耀我们在做减法,而是让评审
明白:本作品的"功能少",是 *想清楚不做什么* 的结果,不是没时间做。

### 1.2 它对谁有 Social Good 意义

我们没有把它包装成一款公益软件,它的社会价值是 *副产品*:

1. **正在消失的街区**:中国一线城市的更新速度,让弄堂蓝 / 砖红墙 / 老招牌的金漆
   在没有任何系统记录的情况下消失。一个普通人散步五分钟就能留下的色彩档案,
   累积起来,就是一份城市的非官方记忆。
2. **色觉障碍者**:模型不仅给 hex,还给 *砖红 / 苔青 / 暮褐* 这种锚定到中国文化
   经验的中文雅名 —— 把视觉信号翻译成语言信号,让看不见颜色的人也能 *谈论* 颜色。
3. **慢下来这件事本身**:在效率工具堆里造一个不催人的角落,是这一代产品很少做的事。

## 2. 模型选型理由

我们不是先选模型,再造产品。我们是先想清楚"用户应该感觉不到 AI 存在",
然后倒推 *什么样的模型* 能撑起这种克制感。

模型在这本图鉴册里只承担两件事,且都必须在用户按下快门后 1-2 秒内完成:

- 看一张照片,选 4 种颜色,起 4 个中文雅名;
- 看调色板和地点,主动调一次工具查街区档案,再写 1 个题名 + 1 句短句。

| 候选                    | 取舍 |
|-------------------------|------|
| Gemma 4 2B              | 视觉编码偏弱,中文雅名生成会退化成"红/蓝/灰"这类大类词,审美维度不及格 |
| **Gemma 4 4B Multimodal** | **本项目所选** |
| Gemma 4 26B MoE         | 推理质量最佳,但 MoE 路由延迟让"按下快门到出结果"破 3s,克制感被打破 |
| Gemma 4 31B Dense       | 同上,且部署成本无法支撑社区免费长期运行 |

**Gemma 4 4B Multimodal** 是 Gemma 4 系列中唯一同时具备 *视觉编码 + 原生函数
调用 + 端侧友好*(bf16 单 24GB GPU 即可)的规格。它刚好够好,但又不会好到
用户察觉它在 *努力* —— 这正是这本图鉴册想要的隐身感。

### 3.1 多模态调色板提取

```python
prompt = (
    "你是一位中文色彩档案员,正在为城市更新前的街景做色彩存档。"
    "看这张照片,选出 4 种最有代表性的颜色。"
    "只回 JSON 数组,每项含 hex 与 zh(2-4 字汉语雅名,"
    "禁用'红/蓝/灰'等大类词,优先用'砖红/暮褐/苔青/茧白'这种文学化命名)。"
)
msgs = [{"role": "user", "content": [
    {"type": "image", "image": img},
    {"type": "text",  "text": prompt},
]}]
```

约束设计要点:

- 用 *档案员* 而不是 *AI 助手* 锚定语气,模型更容易给出文学化命名
- 显式禁用 *红/蓝/灰* 这种大类词,避免模型输出退化为色相分类
- 强制 JSON 输出,后端用正则截取首个数组,容错于模型偶发的解释性前缀

### 3.2 Native Function Calling

Gemma 4 chat template 原生支持 `<tool_call>{...}</tool_call>` 协议。`gemma_client.inscribe_with_tools` 实现了一个 4 步上限的对话循环:

```
turn 1  user → "palette + place"
turn 2  model → tool_call(lookup_district_archive)
turn 3  tool  → {listed: true, tier: "上海第二批历史风貌保护道路"}
turn 4  model → tool_call(save_specimen)
turn 5  tool  → {specimen_no: "No. 0244"}
turn 6  model → 最终题名 + 短句
```

实现要点:

- 工具 schema 在 `gemma_client._archive_tools_schema()` 内,通过 `apply_chat_template(..., tools=tools)` 直接喂给 Gemma 4
- `_parse_tool_calls` 解析 `<tool_call>` 块;模型若直接给出题字而不调工具,循环也会优雅退出
- 这是 *function calling*,不是 *prompt-engineered tool format*。模型自主决定何时调用、调几次

### 3.3 隐私边界

| 数据                | 是否出设备 | 是否落盘 | 是否日志 |
|---------------------|-----------|---------|---------|
| 用户拍摄的原图       | 是(加密 TLS,仅到本机后端) | 应用不持久化;请求期可能临时缓冲 | **否** |
| 图片中的 EXIF/GPS    | 否(Pillow 解码后仅向模型传 RGB 像素) | 否 | 否 |
| 提取的调色板         | 仅 API 响应       | 是(SQLite) | 否 |
| 用户填写的题字        | 仅 API 请求       | 是(SQLite) | 否 |

`backend/main.py` 的 `extract_palette` 函数不会把原图写入业务存储;请求结束后原始上传及框架临时缓冲均被释放。

## 4. 评审标准对齐

| 标准                 | 体现 |
|---------------------|------|
| 架构清晰、模块化      | 路由 / 模型客户端 / 工具 三层分离;同一个 `GemmaClient` 被 stub 与真模型共享接口 |
| Gemma 4 特性利用     | (a) 视觉编码端点 (b) Native Function Calling (c) Chat template 直接喂工具 schema |
| 文档完善             | 一键启动 + Dockerfile + 离线 stub 兜底,评审无需 GPU |
| Social Good 数据合规 | 原图不落盘、隐私边界表格、`sample_data/README.md` 来源标注 |

## 5. 已知局限与后续

1. *端侧推理*:目前依赖 GPU,后续考虑用 `gemma.cpp` + WebGPU 把 4B Multimodal 推到浏览器端,彻底零数据外传。
2. *色彩雅名一致性*:模型偶尔会重新发明名称,实际部署可加一层 vocabulary projection,把输出限定到中国传统色彩词典(色谱集成中)。
3. *社区贡献*:计划开放只读 API,把每个城市的存档导出为 GeoJSON,接入 OpenStreetMap 的颜色图层。
